# ADR-008 — Shared Telegram group practice

Status: Accepted (TASK-079 independent review PASS)
Date: 2026-10-22

## Context and boundary

The owner confirmed private quizzes work and requested group support. ADR-007 remains authoritative for private chats. Extend the same single grammY long-polling process, PostgreSQL and practice scoring helper. Group IDs are delivery scopes, never learner identities. This decision specifies a subsequent implementation; no group feature is implemented or deployed by TASK-079.

## Interaction and authorization

Support `group` and `supergroup`, including separate forum topics. Use `/quiz@thauto_dlt_bot` (or `/practice@thauto_dlt_bot`); grammY must parse the suffix, not a separate leading @mention. Plain commands work when Telegram delivers them. Any authenticated non-bot member may start an idle scope. Default group vehicle CAR; optional `car` or `motorcycle` argument selects the next idle round. English is the initial shared language. Do not read or change the initiator's or voters' personal vehicle, language or reminder settings. Repeated commands reuse the current round; different requested vehicle cannot replace an open round.

Require the bot to be a group administrator before starting scored group practice, so membership checks have Telegram's documented guarantee. Explain this prerequisite in chat rather than silently ignoring a valid command. Do not request destructive privileges. Each actor is a validated positive safe Telegram user ID with is_bot=false; reject sender_chat/anonymous administrators, channels, missing user, forwarded commands and invalid chat/thread IDs. A group chat ID is a negative safe integer within Telegram's 52-bit bound; thread ID is a positive int or normalized 0 for the general/non-topic scope. Derive scope from the original command/callback message, never callback data alone.

Only the initiating member (while still a member) or a current group administrator may finish, advance or replace a round. Other members may vote. Verify permissions using getChatMember outside transactions; accept creator/administrator/member, and restricted only with is_member=true; left/kicked are rejected. Callback data is a short versioned action plus round UUID. Validate current scope, round, callback message ID and topic before acting, including stale or copied controls. Starter/admin privilege is rechecked for each action. Group migration IDs are not learner IDs: invalidate old scope controls and require a new command in the migrated group; do not silently merge identities or replay old polls.

One common non-anonymous native quiz has exactly four options and one correct answer. Reuse ADR-007 text limits, complete stored-language fallback, validated optional media, no runtime translation, no shuffle/revote/add-options/multiple answers. Set protect_content on poll and related messages as forwarding resistance, not an identity guarantee. State that votes are non-anonymous and count toward personal practice. Send no private messages to participants and no forced production test message.

## Additive persistence

Add three models in one additive migration; retain all existing tables and private ChatQuizSession semantics:

* GroupQuizScope: composite primary key (telegramChatId BigInt, threadId Int default 0), nullable unique currentRoundId, and timestamps. A scope serializes command allocation. No User row for a group.
* GroupQuizRound: UUID primary key, scope composite FK, initiating User FK, question/concept FKs, immutable validated presentation snapshot JSON, vehicle/language, delivery state, claimedAt, unique nullable pollId, nullable messageId, createdAt/closedAt. States SENDING, BOUND, UNCERTAIN, CLOSED. Unique (id, chatId, threadId) supports a composite scope-current FK enforcing that the current round belongs to that scope. Add named checks for scope/thread bounds, allowed states and BOUND requiring poll/message IDs. Scope-to-current relation is nullable at creation to avoid circular insertion. Retain historical rounds; one current pointer per scope.
* GroupQuizVote: composite primary key (roundId, userId); unique presentationId; questionId; owned composite FK (presentationId,userId,questionId) to existing QuestionPresentation, plus round relation. A composite (roundId,questionId) FK references a unique round (id,questionId), preventing mismatched question ownership. Each accepted vote creates its own owned presentation with exactly the round snapshot and concept; immutable application logic plus integration tests enforce the copied snapshot. Existing AnswerAttempt.presentationId uniqueness remains the one-answer guard.

Indexes include pollId lookup and scope/history. Foreign keys use Restrict for retained learning history; no destructive cascade from round/scope to learner attempts. Snapshot and round identity fields are immutable after allocation. No group-wide answer is placed in an initiator's private session.

## Delivery and recovery

In a short serializable transaction, lock/create the scope, inspect its current round and reserve at most one SENDING round using existing eligible VERIFIED selection and snapshot validation. Never call Telegram while a transaction is open. Send content/poll afterward and validate Telegram's response against exact chat, thread, quiz type, non-anonymous setting, option order/text and message/poll identifiers before binding. Bind only the unchanged SENDING claim within the same 60-second lease policy as ADR-007. Publish round-bound controls only for the validated delivery. Any ambiguous send/bind failure or expired sending claim becomes UNCERTAIN; no automatic resend. Authorized explicit replacement closes the old capability and allocates a new round. Unknown/unbound/uncertain poll answers never score.

BOUND survives restart and `/quiz` points to its current poll. Finish commits CLOSED first and stops further credit, then calls stopPoll and posts the complete answer/explanation plus Next control. Telegram failures cannot reopen a closed round or undo votes. `/quiz` can recover closed feedback and its Next control; duplicates of feedback are possible and acceptable. Starting the next round requires a matching CLOSED current round; duplicate Next callbacks allocate at most once. Explicit replacement is the only escape for an uncertain send. Do not equate network success with an atomic database/Telegram operation.

The starter/admin can finish after at least one recorded vote (or explicitly replace an uncertain round). Finishing is deliberate: no automatic closure on the first vote or timer. Native Telegram shows correctness to the voter and can show a short native explanation on demand. The bot posts no participant result or full shared answer after each vote. Full explanation and aggregate number answered/accuracy appear only after finish; do not claim Telegram itself prevents every form of answer sharing. Long explanations are shown in full at closure, using existing safe chunking. No leaderboard, user names, scheduled group posts or exam mode in this slice.

## Vote authentication, atomic accounting and polling safety

PollAnswer has no originating chat/thread. Resolve only a server-stored unique round pollId; never infer scope from voter ID or accept an arbitrary presentation from the update. Validate real user, exactly one option index 0..3, no voter_chat; ignore retractions, malformed, unknown and private/group-mismatched bindings. Verify the bot is still administrator and the voter is currently a member of the stored group outside the database transaction. A forwarded poll from a nonmember cannot credit; even a member's forwarded vote is indistinguishable from their in-group vote and is accepted for that bound round. protect_content reduces forwarding but is not relied on as proof.

After membership verification, one short serializable transaction rechecks round BOUND/current/question active+VERIFIED, upserts and locks the same existing User without preference changes, copies the immutable round snapshot into a new owned presentation, inserts the unique GroupQuizVote, and calls submitPracticeAnswer from packages/database/src/answer.ts. Vote linkage, AnswerAttempt and concept counter commit together. Existing vote returns the stored outcome; a replay, changed option or concurrent duplicate never creates a second credit. Lock order for group operations is scope, then round, then User, then presentation; commands acquire no User lock before scope/round. Private operations take User/presentation only and must never acquire a group lock. Use consistent retryDailyPractice conflict handling; all newly introduced paths obey this order.

Any database lookup/transaction failure before a vote is definitively committed or safely rejected throws the existing UnclaimedQuizAnswerError sentinel through configureBotErrors. A transient membership API/transport failure likewise fails safely for retry; an authoritative nonmember or missing required bot privilege is a terminal rejection. All handlers use the existing protectPollingAcknowledgements installed before middleware: normal and SIGTERM/SIGINT stop acknowledgements cannot cross the unfinished/failed vote. Commit-before-ack plus unique vote/presentation constraints means crash replay returns the stored outcome. No new answering lease, queue, scheduler or partial durable vote is needed because every scoring write is in the same transaction. Postcommit UI failures cannot throw the precommit sentinel or undo/duplicate credit.

Dispatch must route each poll answer once using durable bindings; do not let a private handler consume group votes or a failed binding lookup be treated as unknown. Group and private callbacks have disjoint prefixes. Existing private acknowledgement and feedback recovery behavior remains covered by regression tests.

## Sources and consequences

Official Telegram interfaces checked 2026-10-22: [PollAnswer](https://core.telegram.org/bots/api#pollanswer) (real user versus anonymous voter_chat and absence of chat ID), [getChatMember](https://core.telegram.org/bots/api#getchatmember) (administrator guarantee), [sendPoll](https://core.telegram.org/bots/api#sendpoll) (native quiz, message_thread_id, protect_content), [stopPoll](https://core.telegram.org/bots/api#stoppoll), and [privacy-mode command delivery](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get). Only the installed grammY API fields already supported by its types may be used; do not update dependencies just to implement this slice.

This adds durable group state, membership verification and a bot-admin setup prerequisite. It retains established authentication, shared learner accounting, private sessions, Mini App confirmation/exam secrecy and opt-in 11 ICT reminders. TASK-080 must implement and test this decision before a separate exact-release backup/migration/rollout review; accepting this ADR alone enables no production behavior.
